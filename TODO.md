## Design notes and future improvements

* **Concurrency and batching:** I’ve worked with reconciliation files from RBC at Snaplii. The way we handled it was to process the file, insert the data into the database with a status indicator inside a transaction, and then process the data from the database afterward. For a small example file, it’s fine to process transactions one line at a time in a single thread. But in production, the input could have thousands of lines. In that case, it may make sense to process transactions in parallel or batch reconciliation requests before sending them to the remote service. If we take that approach, we’ll need to make sure we preserve the correct order of operations and handle errors consistently across multiple threads.

* **Logging and observability:** The original implementation logged only at the debug level, relied on `transaction.toString()` for output and did not handle nulls gracefully.  In the refactored code we log parsing failures, unknown transaction types and include the offending line for easier troubleshooting.  We also improved the `toString()` method on domain objects to use Jackson so that dates and numbers are consistently rendered as JSON.  For a production system we would also want to attach structured metadata (e.g. MDC or tags) so that logs can be correlated with file names or batch identifiers.

* **Error handling:** The original code would continue execution even after a parsing error but would subsequently throw a `NullPointerException` when logging `transaction.toString()`.  The refactored code catches parsing and number format exceptions, logs the error and proceeds to the next line.  Calls to the reconciliation service are wrapped in a helper that translates failures into a domain-specific `ReconciliationException` with a well-defined type.  Unknown transaction types are logged and ignored.

* **URL validation and configuration:** We currently convert configuration properties (e.g. `contribution.reconciliation.url`) into `java.net.URI` and then into a `URL`.  If the property is not a valid URL a `RuntimeException` is thrown at runtime.  In the future we could validate these properties at application startup and fail fast with a clearer error message.

* **Transaction file location:** The application expects `transaction.file.path` to resolve to a `Path`.  When the property uses the `classpath:` prefix, Spring Boot will still attempt to resolve it to a `Path` and may fail on platforms where the classpath is packaged in a JAR.  We could introduce a custom `@ConfigurationProperties` class that accepts a `Resource` instead of a `Path` and resolves the stream accordingly.  For the purposes of this exercise, the existing behaviour suffices.

* **Test coverage:** We added an end-to-end test that verifies trade settlement processing.  Additional unit tests could be written for `Transaction.toTradeSettlement()` and the `ReconciliationService` helper to ensure proper error translation.  Testing of error scenarios (e.g. malformed lines, HTTP errors) is currently omitted for brevity.
